# Long Form Kindle

Use Long Form's authenticated tools and canonical EPUB → validation → frozen outbox → Resend delivery pipeline. Read [the tool contract](references/tool-contract.md) for inputs, limits, and status meanings.

1. Identify the requested material and whether the user authorized sending. A request to build/install this skill or prepare a packet alone does not authorize an email. Treat “send this to Kindle” as authorization for that specific issue. Preserve the user's authorial boundary: use the writers-packet skill for substantial writing preparation; generate publication prose only when explicitly requested.
2. Discover the connected Long Form tools. Reuse account-linked authentication and its configured Kindle address. Never accept a model-supplied user ID or recipient. When Long Form is absent or requires connection, complete any independent preparation and explain the exact connection needed. Never substitute Gmail, DOCX, a hand-built EPUB, database-inserted sends, or an unreviewed HTTP workaround.
3. Route original web reading to `send_packet(name, urls, dedupe_key)`. Pass public article URLs in reading order; let Long Form extract originals. Preserve full eligible articles rather than manufacturing summaries as replacements. For supplied/generated custom documents, use `send_custom_issue(title, content OR sections, optional source_links, dedupe_key)`. Include only user-requested or user-supplied custom writing. Distinguish custom material from original-author articles. Source links are citations, not requests to fetch article text.
4. Structure custom issues with a concise title and ordered, named sections. Preserve existing text, code, tables, and links. Default to literal text; use safe semantic HTML for headings, lists, tables, code blocks, and source links. Do not pass Markdown as HTML or silently replace complete content with excerpts. Include an exercise only when requested or already supplied. Do not pad to a reading-time target; report when eligible material cannot satisfy it.
5. For a send, create a stable `dedupe_key` for this logical request (for example `langgraph:2026-10-03:v1`) and retain it with the returned job ID. Reuse the same key and identical content after uncertain responses. A changed payload needs an explicitly distinct delivery request; never evade a conflict or failure by generating new keys automatically. Sending tools queue delivery immediately; call them only after authorization.
6. Capture `job.id` and check `get_packet_status(job_id)`. Follow queued/running work to a terminal status with bounded checks; if still pending, report the job ID and pending state rather than claiming success. Inspect error, warnings, QA, and provider ID. Use `get_delivery_history` as supporting evidence when available; an empty history is not a reason to resend.
7. Report the title and precise observed state. `sent` means Resend accepted the email, not that Amazon imported it or it appeared in Kindle. `partial` means accepted with omissions: identify them. `failed`/`needs_review` means do not retry blindly. Never claim Kindle receipt from provider acceptance alone. Explain configured sender approval only when an observed Kindle ingestion problem makes it relevant.

Keep progress and completion messages short. If project state materially changes, synchronize the existing Trello card according to the user's operating manual and link to source systems.
